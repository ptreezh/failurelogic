# Production-readiness Audit — 2026-09-07

> Goal: project fully production-ready, users can experience "The Logic of Failure"
> interactively. Each finding has a fix committed separately.

## Test methodology

1. Started backend (`python api-server/start.py 8000`) — confirmed healthy via `/health`
2. Real curl against user-facing endpoints: `/scenarios/`, `/scenarios/{id}`,
   `/scenarios/create_game_session`, `/scenarios/{game_id}/turn`
3. Created a real game session, played 5+ turns, observed state evolution
4. Compared data flow end-to-end against intended user experience

## P0 — Blockers (user cannot play)

### P0-1: Scenario ID mismatch between API and logic layer

**Symptom**: User picks "咖啡店场景", makes 5 decisions. State never changes
(resources=1000, satisfaction=50, reputation=50 throughout).

**Root cause**: API serves scenario IDs from `start.py:BASE_SCENARIOS`:
- `coffee-shop-nonlinear-effects`
- `investment-information-processing`

But `logic/turn_executor.py:execute_real_logic()` dispatches on the OLD IDs:
- `coffee-shop-linear-thinking` (line 36)
- `investment-confirmation-bias` (line 253)

`relationship-time-delay` matches in both. The other 2 scenarios fall through to
the no-op fallback (lines 510-518), so state never updates.

**Impact**: 2/3 scenarios are broken — user makes decisions but the world
doesn't respond. Educational experience is meaningless.

**Fix**: Add alias branches in `turn_executor.py` for the new IDs that delegate
to the existing logic (or rewrite the logic for the new bias content —
the names reflect different biases than the original). Decision pending.

### P0-2: API response size grows exponentially per turn

**Symptom**: Response file sizes:
- turn 2: 223 KB
- turn 3: 447 KB
- turn 4: 894 KB

Each turn approximately doubles the response size.

**Root cause**: `start.py:execute_turn()` builds the new `game_state` by
copying `current_state` and appending the new decision record:
```python
new_state["decision_history"] = current_state.get("decision_history", []) + [decision_record]
```

And `decision_record["result_state"] = new_state.copy()` — so each turn
embeds the ENTIRE game state (which itself contains the full history).
N turns → response size O(2^N).

**Impact**: After ~15 turns, response is hundreds of MB. Mobile users
will time out. Server memory grows unboundedly. PWA cache fills up.

**Fix**: Don't embed `result_state` in the decision record. Either:
- (A) Store only the decision diff and the state at that turn
- (B) Drop `result_state` entirely; client reconstructs from history + final state

Decision pending.

### P0-3: Feedback is always the same template string

**Symptom**: After 5 turns, every feedback response is:
"合理的员工配置提升了客户满意度。"

regardless of the actual decision (hire_staff, increase price, etc.).

**Root cause**: Symptom of P0-1 — state never changes, so the feedback
generator falls back to a template. Once P0-1 is fixed, this should
resolve naturally. Will verify.

## P1 — Important (degraded experience)

### P1-1: Game sessions live in memory only

**Symptom**: `game_sessions` is a module-level dict in `start.py`. Restart
the server, all sessions lost.

**Impact**: User in the middle of a 15-turn scenario, server restart (deploy,
crash), they lose all progress.

**Fix**: Persist to disk or accept the limitation explicitly in the UI.

### P1-2: Multi-stage feedback branches may not all be exercised

**Symptom**: Per CLAUDE.md, turn 3 reveals biases, turn 4+ gives
personalized insights. I observed `has_personalized_insight: true` from
turn 2 onwards. But the actual content was always the same template.

**Impact**: If P0-1 fix makes feedback work, need to verify each branch
turn 1, 2, 3, 4+ produces meaningfully different content.

### P1-3: CORS allows all origins

**Symptom**: `app.add_middleware(CORSMiddleware, allow_origins=["*"])`

**Impact**: Production exposure — any origin can call the API. Not great
if rate limiting or auth is added later. For now it's intentional
(GH Pages + Render backend, no auth). Document the decision.

## P2 — Nice-to-have

### P2-1: `api-server/data/scenarios.py` is dead code

**Symptom**: Imported nowhere (search confirms). The actual scenarios
come from `start.py:BASE_SCENARIOS`. This file is misleading maintenance
hazard — it implies scenarios load from there.

**Fix**: Delete or document its purpose.

### P2-2: Game scenarios JSON files referenced but missing

**Symptom**: `start.py:load_additional_scenarios()` reads
`game_scenarios.json`, `advanced_game_scenarios.json`,
`historical_cases.json`. None exist in `api-server/data/`.

**Impact**: Only 3 scenarios available. The "advanced challenges" inside
each scenario provide some variety, but real expansion needs the data
files. They're in `archived-scenarios/api-server/data/`.

**Fix**: Either restore the JSON files from archive or remove the loading
code.

### P2-3: Backend has no rate limiting

**Symptom**: No throttling on `/scenarios/create_game_session` or `/turn`.

**Impact**: An attacker could spam session creation and exhaust server
memory. Or cost money on Render.

**Fix**: Add per-IP rate limiter (e.g., `slowapi` middleware).
